Mục lục

Hướng dẫn setup VPS và đưa website lên mạng

Phiên bản chi tiết: từ lúc nhận VPS trống đến khi website chạy HTTPS với tên miền riêng, có cơ sở dữ liệu, quy trình deploy, backup và giám sát.

Áp dụng cho Ubuntu 22.04 / 24.04 LTS (Debian tương tự). Thời gian ước tính: 1,5 - 3 giờ cho lần đầu.

0. Cách sử dụng tài liệu

0.3. Những sai lầm phổ biến của người mới

  • Chạy mọi thứ bằng root và để đăng nhập bằng mật khẩu, dễ bị dò mật khẩu chỉ sau vài giờ.
  • Mở cổng database (5432, 3306, 6379...) ra Internet.
  • Commit file .env hoặc private key lên Git.
  • Không bật firewall, hoặc bật firewall nhưng quên mở SSH nên tự khóa mình.
  • Không có backup, chỉ nhận ra khi đã mất dữ liệu.
  • Sửa file cấu hình Nginx nhưng quên chạy nginx -t trước khi reload.
  • Build Next.js trên VPS 1 GB RAM không có swap, tiến trình bị kill.

2. Chuẩn bị

2.1. Thông tin cần có

  • IP public của VPS (IPv4, có thể có IPv6).
  • Tài khoản root và mật khẩu (hoặc SSH key nhà cung cấp gửi).
  • Tên miền và quyền quản lý DNS (Cloudflare, Mắt Bão, PA Vietnam, Namecheap...).
  • Source code website, tốt nhất đã đẩy lên Git (GitHub/GitLab).
  • Máy cá nhân có terminal: Linux/macOS dùng sẵn; Windows 10/11 dùng PowerShell hoặc Windows Terminal (đã tích hợp ssh).

2.2. Chọn cấu hình VPS tham khảo

Loại websiteRAMCPUỔ đĩaGhi chú
Static / landing page512 MB - 1 GB1 vCPU10 GBNginx là đủ
Node.js nhỏ (Next.js + API)2 GB1-2 vCPU20-40 GBNên thêm swap; build Next.js tốn RAM
Nhiều service + database4 GB trở lên2 vCPU40-80 GBCân nhắc Docker Compose

Với người dùng ở Việt Nam, chọn nhà cung cấp có node tại Việt Nam, Singapore hoặc Hồng Kông để độ trễ thấp. Chọn Ubuntu LTS (22.04 hoặc 24.04) vì tài liệu và cộng đồng nhiều nhất.

2.3. Tạo SSH key trên máy cá nhân (nếu chưa có)

Private key giữ bí mật tuyệt đối; public key đưa lên VPS. Nên đặt passphrase.

# [LOCAL]
ssh-keygen -t ed25519 -C "email-cua-ban@example.com"
# Enter để dùng đường dẫn mặc định ~/.ssh/id_ed25519, nhập passphrase

cat ~/.ssh/id_ed25519.pub          # public key: một dòng bắt đầu bằng ssh-ed25519
Mẹo Windows PowerShell: type $env:USERPROFILE\.ssh\id_ed25519.pub

2.4. Cấu hình ~/.ssh/config để gõ lệnh ngắn hơn

# [LOCAL] file ~/.ssh/config
Host myvps
    HostName 102.245.237.2
    User haidang
    IdentityFile ~/.ssh/id_ed25519
    ServerAliveInterval 60

Sau đó chỉ cần gõ ssh myvps.

4. Cập nhật hệ thống và cấu hình cơ bản

4.1. Update gói và cài công cụ nền tảng

# [VPS] với quyền root
apt update && apt upgrade -y
apt install -y curl wget git ufw fail2ban unzip htop ncdu nano ca-certificates gnupg software-properties-common

Các gói thêm gồm công cụ tải file (curl, wget), Git, firewall (ufw), chống dò mật khẩu (fail2ban), theo dõi tài nguyên (htop) và xem dung lượng thư mục (ncdu).

Nếu apt báo Could not get lock, VPS đang tự chạy cập nhật nền. Chờ 1-2 phút rồi chạy lại, không xóa file lock.

4.2. Timezone, hostname, locale

timedatectl set-timezone Asia/Ho_Chi_Minh
timedatectl                         # kiểm tra giờ hiện tại và NTP đang bật
hostnamectl set-hostname my-vps     # tùy chọn

Đồng hồ chính xác quan trọng vì chứng chỉ SSL, log và cron đều phụ thuộc vào thời gian.

4.3. Khởi động lại nếu cần

ls /var/run/reboot-required && reboot    # chỉ reboot khi hệ thống yêu cầu

Đợi khoảng 30-60 giây rồi SSH lại.

5. Tạo user riêng và bảo mật SSH

Không nên chạy website hoặc thao tác hằng ngày bằng root. Tạo user thường có quyền sudo.

5.1. Tạo user haidang

# [VPS] root
adduser haidang                    # nhập mật khẩu mạnh
usermod -aG sudo haidang
id haidang                         # phải thấy nhóm sudo

5.2. Đưa SSH key cho user haidang

Cách 1 (từ máy cá nhân, đơn giản nhất):

# [LOCAL]
ssh-copy-id haidang@102.245.237.2

Cách 2 (thủ công, dùng khi máy không có ssh-copy-id, ví dụ Windows):

# [VPS] root
mkdir -p /home/haidang/.ssh
nano /home/haidang/.ssh/authorized_keys      # dán public key, mỗi key một dòng
chown -R haidang:haidang /home/haidang/.ssh
chmod 700 /home/haidang/.ssh
chmod 600 /home/haidang/.ssh/authorized_keys

Mở terminal mới và kiểm tra:

# [LOCAL]
ssh haidang@102.245.237.2
# [VPS] sau khi vào
sudo whoami                      # nhập mật khẩu haidang, kết quả phải là: root
Nếu vẫn bị hỏi mật khẩu khi SSH bằng key, nguyên nhân gần như luôn là sai quyền (.ssh phải 700, authorized_keys phải 600) hoặc sai chủ sở hữu (phải là haidang).

5.3. Khóa đăng nhập root và đăng nhập bằng mật khẩu

Chỉ làm bước này SAU KHI đã đăng nhập thành công bằng user haidang + SSH key, và GIỮ NGUYÊN phiên root cũ đang mở để phòng khi cấu hình sai.
# [VPS]
sudo nano /etc/ssh/sshd_config

PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
KbdInteractiveAuthentication no
MaxAuthTries 3
LoginGraceTime 30

sudo sshd -t                       # kiểm tra cú pháp: không in gì là đúng
sudo systemctl restart ssh

PasswordAuthentication noChỉ cho đăng nhập bằng SSH key, vô hiệu hóa dò mật khẩu

sudo sshd -T | grep -Ei "permitrootlogin|passwordauthentication"
# Kết quả mong đợi:
permitrootlogin no

Cuối cùng, mở terminal thứ ba để xác nhận: ssh root@102.245.237.2 phải bị từ chối, còn ssh haidang@102.245.237.2 vẫn vào bình thường.

5.4. Đổi cổng SSH (tùy chọn)

Đổi cổng chỉ giúp giảm nhiễu log, không phải biện pháp bảo mật thực chất. Ubuntu 24.04 dùng socket activation (ssh.socket) nên việc đổi cổng phức tạp hơn; người mới có thể bỏ qua.

6. Firewall (UFW), Fail2ban và tự cập nhật bảo mật

Ba lớp bảo vệ: UFW chặn cổng thừa, Fail2ban chặn kẻ dò mật khẩu, unattended-upgrades tự vá lỗi hệ thống.

6.1. Firewall hoạt động như thế nào

Gói tin đến VPS
      |
      v
Thuộc kết nối đã được chấp nhận trước đó? --có--> cho qua (firewall có trạng thái)
      | không
      v
Duyệt danh sách rule từ TRÊN XUỐNG, rule đầu tiên khớp sẽ được áp dụng
      | không rule nào khớp
      v
Chính sách mặc định (default): với incoming là deny -> gói tin bị chặn
  • Incoming / outgoing: incoming là kết nối từ ngoài vào VPS; outgoing là VPS chủ động gọi ra ngoài (apt update, git clone, gọi API).
  • Chính sách mặc định: hành động khi không rule nào khớp. Cách an toàn là chặn hết, chỉ mở cái cần (whitelist).
  • Firewall có trạng thái: gói tin trả lời cho kết nối do VPS khởi tạo, hoặc thuộc phiên SSH đang mở, tự động được cho qua.

6.2. Phân tích từng lệnh cấu hình UFW

Lệnh 1: chặn chiều vào mặc định

sudo ufw default deny incoming
Thành phầnÝ nghĩa
sudoChạy với quyền quản trị, vì cấu hình firewall cần root
ufwChương trình quản lý firewall
defaultĐặt chính sách mặc định
denyChặn và bỏ qua gói tin, không phản hồi gì cho phía gửi
incomingÁp dụng cho kết nối từ ngoài vào VPS

Lệnh này chưa có tác dụng ngay cho đến khi ufw enable. reject gửi lại thông báo từ chối; deny im lặng, làm chậm việc dò quét. VPS thường dùng deny.

Lệnh 2: cho phép chiều ra

sudo ufw default allow outgoing

Nếu chặn chiều này, apt update, certbot (liên lạc Let's Encrypt), gọi API bên thứ ba, gửi email đều hỏng.

Lệnh 3: cho phép SSH kèm giới hạn tốc độ

sudo ufw limit OpenSSH
Thành phầnÝ nghĩa
limitGiống allow nhưng chặn tạm IP mở từ 6 kết nối trở lên tới cổng này trong 30 giây
OpenSSHTên application profile, thực chất là cổng 22/tcp. Xem: sudo ufw app list, sudo ufw app info OpenSSH
LệnhCổngGiới hạn tốc độKhi nào dùng
ufw allow OpenSSH22/tcpKhôngTự động hóa bằng nhiều kết nối liên tiếp
ufw limit OpenSSH22/tcpCóKhuyến nghị cho SSH thông thường
ufw limit 2222/tcp2222/tcpCóKhi đã đổi cổng SSH sang 2222
Nếu script deploy hoặc CI mở rất nhiều kết nối SSH liên tiếp từ cùng một IP (ví dụ GitHub Actions), rule limit có thể chặn nhầm. Khi đó chuyển sang allow cho IP nguồn hoặc allow thường.

Lệnh 4 và 5: mở cổng web

sudo ufw allow 80/tcp
sudo ufw allow 443/tcp

Thiếu phần /tcp thì UFW mở cho cả TCP lẫn UDP, rộng hơn mức cần. Nếu sau này bật HTTP/3 (QUIC, UDP), thêm sudo ufw allow 443/udp.

Sau khi cài Nginx có thể dùng hồ sơ ứng dụng: 'Nginx HTTP' (80/tcp), 'Nginx HTTPS' (443/tcp), 'Nginx Full' (cả hai). Dấu nháy đơn bắt buộc vì tên có dấu cách.

Lệnh 6: bật firewall

sudo ufw enable

# Kết quả mong đợi:

Thứ tự đúng: allow/limit SSH, kiểm tra lại, rồi mới enable. Xem các rule đã thêm trước khi bật: sudo ufw show added, phải thấy SSH trong đó.

6.3. Cú pháp rule chi tiết và thứ tự ưu tiên

Dạng đầy đủ: ufw [hành động] [chiều] from [nguồn] to [đích] port [cổng] proto [giao thức].

Mục đíchLệnhGiải thích
Mở cổng cho mọi ngườiufw allow 8080/tcpRule đơn giản nhất
Chỉ cho 1 IP vào 1 cổngufw allow from 203.0.113.10 to any port 5432 proto tcpMọi IP khác vẫn bị chặn theo default
Chỉ cho một dải mạngufw allow from 203.0.113.0/24 to any port 22/24 nghĩa là 256 địa chỉ
Chặn hẳn 1 IPufw deny from 198.51.100.7Chặn mọi cổng từ IP đó

Rule khớp đầu tiên thắng. Nếu đã có rule allow cho cổng 80 ở trên, một rule deny from thêm sau cùng sẽ không có tác dụng với IP đó. Muốn chặn có hiệu lực, chèn lên trên: sudo ufw insert 1 deny from 198.51.100.7.

Khi xóa nhiều rule theo số, xóa từ số lớn về số nhỏ.

6.6. Tình huống thực tế

Chỉ cho IP văn phòng/nhà vào SSH (chặt nhất):

sudo ufw delete limit OpenSSH
sudo ufw allow from 203.0.113.10 to any port 22 proto tcp
sudo ufw status numbered
Chỉ dùng khi IP nhà mạng cố định. IP thay đổi sẽ khiến bạn tự khóa mình. Luôn biết cách vào bằng console của nhà cung cấp VPS.

Cho một IP truy cập database để quản trị (xong việc thì đóng lại):

sudo ufw allow from 203.0.113.10 to any port 5432 proto tcp
sudo ufw delete allow from 203.0.113.10 to any port 5432 proto tcp

Cách an toàn hơn vẫn là SSH tunnel (mục 12.1).

Mở cổng tạm để thử ứng dụng:

sudo ufw allow 3000/tcp              # thử truy cập http://102.245.237.2:3000
sudo ufw delete allow 3000/tcp       # đóng lại ngay khi xong

Bị khóa ra khỏi VPS: vào console/VNC trong panel nhà cung cấp (không cần SSH), đăng nhập và sửa:

sudo ufw allow OpenSSH           # thêm lại rule SSH
# hoặc tạm tắt để vào lại rồi cấu hình sau:
sudo ufw disable

6.8. Fail2ban: cơ chế và cấu hình

UFW quyết định cổng nào mở. Cổng SSH phải mở, nên kẻ tấn công vẫn gõ được vào đó. Fail2ban đọc log, phát hiện IP thất bại nhiều lần và tự thêm rule chặn IP đó.

7.3. Nếu dùng Cloudflare

  • Đám mây cam (Proxied): traffic đi qua Cloudflare, ẩn IP thật, có CDN và bảo vệ cơ bản.
  • Đám mây xám (DNS only): trỏ thẳng về VPS.
  • Khi cấp SSL bằng certbot kiểu HTTP-01, để xám tạm thời, cấp xong bật lại cam.
  • Ở SSL/TLS chọn chế độ Full (strict). Tránh Flexible vì gây vòng lặp chuyển hướng và kết nối Cloudflare đến VPS không mã hóa.
  • Khi bật proxy, IP Nginx thấy là IP Cloudflare; muốn log IP thật, cấu hình real_ip (mục 7.5).

7.4. Trỏ tên miền mua tại Cloudflare về VPS (từng bước)

Mua domain ngay tại Cloudflare Registrar thì DNS đã có sẵn, không cần đổi nameserver. Nếu domain mua nơi khác, phải đổi nameserver sang hai nameserver Cloudflare cung cấp và chờ trạng thái Active.

  1. Đăng nhập dash.cloudflare.com.
  2. Ở Account Home, bấm vào tên miền (haiphan.org).
  3. Thanh bên trái chọn DNS, rồi Records.
  4. Nếu có sẵn bản ghi A, AAAA hoặc CNAME cho tutor (hoặc @, www) do trang đỗ tên miền tạo, xóa hoặc sửa. Một tên không được vừa có CNAME vừa có A.
  5. Bấm Add record và điền: Type A; Name tutor; IPv4 address 102.245.237.2; Proxy status DNS only (xám) trong lúc setup; TTL Auto. Bấm Save.
  6. Bản ghi gốc @ (tùy chọn, chỉ khi muốn haiphan.org cũng mở được, xem mục 13.3) cũng dùng A, DNS only.
  7. Kiểm tra: dig +short tutor.haiphan.org và dig +short tutor.haiphan.org @1.1.1.1, phải ra 102.245.237.2. Chỉ khi xám, dig mới trả IP VPS; bật cam thì dig trả IP Cloudflare (bình thường).
Cấp SSL (bước 6) khi bản ghi còn xám, sau đó mới bật proxy cam và đặt SSL/TLS = Full (strict), tránh lỗi chuyển hướng.

7.5. Lấy đúng IP người dùng khi bật proxy Cloudflare

Khi bật proxy, mọi request đến Nginx đều từ IP Cloudflare, nên log, rate limit và Fail2ban chỉ thấy IP Cloudflare. Cloudflare gửi IP thật trong header CF-Connecting-IP; Nginx chỉ nên tin header này khi request đến từ dải IP Cloudflare:

{
  for f in ips-v4 ips-v6; do
    for ip in $(curl -s https://www.cloudflare.com/$f); do
      echo "set_real_ip_from $ip;"
    done
  done
  echo "real_ip_header CF-Connecting-IP;"
} | sudo tee /etc/nginx/conf.d/cloudflare-realip.conf

sudo nginx -t && sudo systemctl reload nginx

Danh sách IP Cloudflare có thể thay đổi nên cần cập nhật định kỳ. Nếu truy cập thẳng bằng IP hoặc để xám mà vẫn dùng file này thì không sao, vì header chỉ được tin khi nguồn nằm trong dải đã khai báo.

7.6. Cổng nào đi qua proxy Cloudflare được

HTTP: 80, 8080, 8880, 2052, 2082, 2086, 2095. HTTPS: 443, 2053, 2083, 2087, 2096, 8443. Các cổng khác bị bỏ qua khi bật proxy.

  • Webmin (cổng 10000) và nhiều trang quản trị không nằm trong danh sách: để subdomain panel ở chế độ DNS only (xám), hoặc dùng SSH tunnel.
  • SSH (cổng 22) không đi qua proxy. Bản ghi dùng để SSH phải DNS only; đơn giản hơn là SSH thẳng bằng IP.
  • Bật proxy ẩn IP thật khỏi DNS nhưng không làm VPS tự an toàn: UFW và SSH hardening vẫn cần. Nếu một bản ghi xám khác trỏ cùng IP thì IP VPS vẫn lộ.
  • WebSocket vẫn chạy qua proxy trên cổng 80/443 nếu Nginx đã cấu hình Upgrade (mục 10.6).

7.7. Hai cách cấp SSL khác khi dùng Cloudflare (tùy chọn)

Cách A: Cloudflare Origin Certificate. Chứng chỉ Cloudflare cấp cho đoạn Cloudflare tới VPS, hạn rất dài (tối đa 15 năm). Chỉ hợp lệ khi domain bật proxy; truy cập thẳng bằng IP sẽ báo không tin cậy.

  1. Cloudflare, SSL/TLS, mục Origin Server, bấm Create Certificate, chọn tutor.haiphan.org (hoặc *.haiphan.org).
  2. Sao chép Origin Certificate và Private Key. Private key chỉ hiện một lần, lưu ngay.
  3. Trên VPS tạo hai file và đặt quyền chặt:
sudo mkdir -p /etc/ssl/cloudflare
sudo nano /etc/ssl/cloudflare/tutor.haiphan.org.pem          # dán Origin Certificate
sudo nano /etc/ssl/cloudflare/tutor.haiphan.org.key          # dán Private Key
sudo chmod 600 /etc/ssl/cloudflare/tutor.haiphan.org.key

server {
    listen 443 ssl;
    http2 on;
    server_name tutor.haiphan.org;
    ssl_certificate     /etc/ssl/cloudflare/tutor.haiphan.org.pem;
    ssl_certificate_key /etc/ssl/cloudflare/tutor.haiphan.org.key;
    # ... phần location proxy_pass như mục 10.6
}

Cách B: Let's Encrypt qua DNS-01 với API token Cloudflare. Không cần cổng 80, cho phép wildcard (*.haiphan.org). Certbot tự tạo bản ghi TXT tạm trong DNS Cloudflare.

  1. Cloudflare, My Profile, API Tokens, Create Token, mẫu Edit zone DNS, giới hạn Zone Resources vào đúng domain.
  2. Sao chép token (chỉ hiện một lần) và lưu trên VPS với quyền chặt.
  3. Cài plugin và chạy certbot:
sudo apt install -y python3-certbot-dns-cloudflare
sudo mkdir -p /root/.secrets
sudo nano /root/.secrets/cloudflare.ini
# nội dung: dns_cloudflare_api_token = DAN_TOKEN_CUA_BAN_VAO_DAY
sudo chmod 600 /root/.secrets/cloudflare.ini

sudo certbot certonly --dns-cloudflare \
  --dns-cloudflare-credentials /root/.secrets/cloudflare.ini \
  -d haiphan.org -d '*.haiphan.org'

Chứng chỉ nằm ở /etc/letsencrypt/live/haiphan.org/, bạn tự khai báo vào Nginx (certonly không tự sửa Nginx).

API token là bí mật như mật khẩu: không commit lên Git, không gửi cho người khác. Thu hồi ngay trong Cloudflare nếu nghi ngờ lộ.

  pm2 reload all --update-env
  exit 1
}
trap rollback ERR

npm ci

16.4. Quản lý bí mật (secret)

  • Mỗi môi trường (dev/production) dùng secret khác nhau; secret production chỉ tồn tại trên VPS hoặc trong hệ thống secret của CI.
  • Đổi secret khi có người rời dự án hoặc nghi ngờ lộ.
  • Nếu lỡ commit secret lên Git: coi như đã lộ, đổi ngay. Chỉ xóa commit là chưa đủ.
  • Dùng git-secrets hoặc GitHub secret scanning để phát hiện sớm.

16.5. Nguyên tắc quyền tối thiểu

  • Ứng dụng chạy bằng user thường, không chạy bằng root.
  • User database chỉ có quyền trên đúng database của app.
  • Key CI chỉ được phép chạy deploy (có thể giới hạn bằng command="..." trong authorized_keys).
  • Gỡ SSH key của người không còn tham gia dự án khỏi authorized_keys.
